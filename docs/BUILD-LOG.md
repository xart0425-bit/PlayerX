# PlayerX 개발 기록

## 2026-09-06 — 앞 탭 그림이 비쳐 보이던 것 (해결)

며칠 쫓던 것이다. 재생 탭에서 파일을 연 뒤 비교 탭으로 넘어가면 재생 탭 화면이
비교 탭 영상 자리에 그대로 남아 보였다.

### 왜 이렇게 오래 걸렸나 — 도구가 거짓말을 했다

`QWidget.grab()` 으로 위젯을 그려 보면 **언제나 깨끗했다.** Qt 도 재생 탭이
`isVisible() == False` 라고 답했다. 그래서 "화면 갱신 문제겠지" 로 몰고
엉뚱한 것들을 계속 시도했다 — 배경 채우기, `repaint()`, 창을 옮겼다 되돌리기,
창을 숨겼다 보이기, 네이티브 창 강제 이동, `WA_DontCreateNativeAncestors` 제거.
전부 헛수고였다.

**`grab()` 은 네이티브 자식 창을 빼고 그린다.** mpv 위젯이 바로 그 네이티브
자식 창이다. 그래서 진짜 화면을 못 보고 있었던 것이다.

방향을 바꿔 **윈도우에게 "네 내용을 직접 그려라"라고 시켰다**(`PrintWindow`
+ `PW_RENDERFULLCONTENT`). 거기서는 문제가 그대로 찍혔다. 캡처 방식 문제가
아니라 **진짜로 화면에 그렇게 나오고 있었다**는 게 그때 확실해졌다.

### 원인 — 칠하겠다고 약속해 놓고 안 칠했다

```python
self.setAttribute(Qt.WA_OpaquePaintEvent)   # "바탕은 내가 칠한다"
self.setStyleSheet("background-color: #000;")
```

`WA_OpaquePaintEvent` 는 **"이 위젯은 자기 바탕을 스스로 칠하니 Qt 는 손대지
말라"**는 약속이다. Qt 는 그 말을 믿고 배경을 안 칠한다 — 스타일시트 배경도
안 그린다. 그런데 `MpvWidget` 에는 `paintEvent` 가 없었다.

영상이 올라와 있을 때는 mpv 가 그 창에 직접 그리니 아무 문제가 없었다.
**파일이 없을 때**가 문제였다 — mpv 도 안 그리고 Qt 도 안 그리니, 그 네이티브
창에는 그 자리에 예전에 있던 그림이 그대로 남았다. 그게 재생 탭 화면이었다.

고친 건 다섯 줄이다.

```python
def paintEvent(self, event) -> None:
    QPainter(self).fillRect(event.rect(), QColor(0, 0, 0))
```

### 검사 — 위젯을 그려 보는 방식으로는 못 잡는다

`smoke_compare.py` 에 `[F]` 를 넣었다. 밝은 그림을 그려 놓고 **그 위에 파일 없는
mpv 위젯을 덮은 뒤 `PrintWindow` 로 실제 화면을 받아** 검은지 본다.

일부러 `paintEvent` 를 비워서 검사가 진짜로 잡는지 확인했다:

```
고장 냈을 때  밝은 픽셀 87.38%   -> 실패
고친 상태     밝은 픽셀  0.00%   -> 통과
```

**검사 도구 5종 전부 통과.**

## 2026-09-06 — '영상 열기' 를 눈에 보이게

여는 방법이 메뉴(☰)와 `Ctrl+O`, 드래그앤드롭뿐이었다. 처음 켠 사람은 무엇을
눌러야 할지 알 수가 없다. 세 자리에 넣었다.

- **영상 자리** — 파일이 없으면 영상이 들어올 그 자리에 안내가 뜬다.
  폴더 아이콘 · "영상을 열어 주세요" · 파란 **영상 열기** 버튼 · 단축키와
  지원 확장자. 파일을 열면 안내가 빠지고 영상이 들어온다 (`QStackedWidget`).
- **헤더** — 파일이 열려 있을 때도 늘 손 닿는 자리에 `영상 열기` 버튼.
- **비교·트림 탭** — 기존 `열기…` 를 `A 열기` · `B 열기` · `영상 열기` 로
  바꾸고 파란 테두리(`#AccentButton`)를 줬다. 이 탭에서 제일 먼저 누를 버튼이다.

### 남은 문제 — 아직 못 고쳤다

재생 탭에서 파일을 연 뒤 비교 탭으로 넘어가면, **앞 탭(재생)의 그림이 비교 탭
화면에 남아 겹쳐 보이는 일**이 있다. 스크린샷으로 재현된다.

알아낸 것까지 적어 둔다.

- 위젯 트리 자체는 멀쩡하다. `w.grab()` (위젯을 직접 그려 보는 것)은 깨끗하고,
  Qt 도 재생 탭이 `isVisible() == False` 라고 답한다.
- 원인은 **mpv 때문에 이 앱의 위젯이 거의 다 네이티브 창으로 승격된다**는 데
  있어 보인다. 윈도우 API 로 세어 보면 QLabel·QPushButton·QSpinBox 까지 전부
  진짜 창이다. 그중 mpv 창 두 개가 부모(CompareView)보다 **44px 아래**에
  놓여 있었다 — Qt 가 아는 좌표와 실제 창 위치가 어긋나 있다.
- 그 상태에서는 같은 좌표를 다시 줘도 Qt 가 "안 바뀌었다"며 창을 안 옮긴다.
- 시도해서 **안 된 것**: 탭 페이지·탭 위젯에 `autoFillBackground`, 창 전체
  `repaint()`, 창을 옮겼다 되돌리기, 창을 숨겼다 다시 보이기,
  `showEvent` 에서 한 번 더 배치, 네이티브 창을 1px 옮겼다 되돌려 강제 이동.

**한 가지는 확실히 걷어냈다.** 리사이즈 중 그림 찢어짐을 줄이려고 넣었던
배치 스로틀(30ms 로 묶기)이 저 좌표 어긋남을 **만들고 있었다.** 되돌렸다 —
`CompareView.resizeEvent` 는 다시 그 자리에서 배치한다.

**검증** — 검사 도구 5종 전부 통과.

## 2026-09-06 — 비교 탭이 처음 열릴 때 2초 걸리던 것 · 타임코드가 떨리던 것

### 탭을 만들어서 옮기지 말고, 그 자리에서 만들 것

비교 탭을 처음 누르면 2초쯤 멈췄다. 재 보니 이상했다 —

```
MpvWidget 하나 만들기          169 ms
비교 탭 만들기 (mpv 2개 포함)  2132 ms   <- 앞뒤가 안 맞는다
```

프로파일을 뜨니 `ComparisonTab` 을 만드는 데는 **10ms** 뿐이었고, 2초는
그 위젯을 탭 페이지 레이아웃에 **집어넣는 줄**에서 나왔다.

이유는 mpv 위젯이 네이티브 창을 갖기 때문이다. `ComparisonTab(self)` 로
창을 부모 삼아 만들어 두었다가 나중에 탭 페이지로 옮기면(reparent),
Qt 는 그 안의 네이티브 창을 **부수고 다시 만든다.** mpv 두 개가 초기화를
두 번씩 한 셈이다.

**처음부터 그 페이지의 자식으로 만든다.** 옮기는 일이 아예 없어진다.

| | 전 | 후 |
|---|---|---|
| 비교 탭 처음 열기 | 2132 ms | **171 ms** |
| 트림 탭 처음 열기 | 1619 ms | **245 ms** |

트림 탭에는 하나가 더 있었다 — 이 ffmpeg 빌드에 실제로 있는 인코더만 콤보에
채우려고 `ffmpeg -encoders` 를 돌리는데, 외부 프로세스라 0.34초가 걸린다.
결과는 어차피 캐시되므로 **앱을 켤 때 백그라운드 스레드로 미리 받아 둔다**
(`MainWindow._warm_ffmpeg_cache`). 탭은 캐시된 값을 그냥 집어 간다.

### 영상은 안 흔들리는데 타임코드 글자만 떨리던 것

앞서 라벨 **높이**를 못박아서 영상과 타임라인은 제자리에 섰다. 그런데 글자는
여전히 떨렸다. 고정된 높이 **안에서** 글자를 가운데 맞추는데, 한글이 섞이면
그 줄의 글꼴 지표가 달라져 가운데가 1px 옮겨 가기 때문이다. 높이를 고정해도
글자 위치는 고정되지 않는다.

그래서 **카운터에는 한글을 아예 넣지 않기로 했다.** 어긋남·오프셋은 바로 옆
`drift_label`(본문 글꼴)로 옮겼다 — 정보는 그대로 보이고, 카운터는 숫자와
타임코드만 담는다.

검사도 좌표만 보던 것에서 한 겹 더 들어갔다. `smoke_compare.py` [E] 는 이제
**라벨을 직접 그려서 글자가 시작하는 픽셀 줄**을 비교한다. 위젯 좌표로는
이 종류의 흔들림을 절대 못 잡기 때문이다. 비교에 쓰는 문자열은 재생 중에
실제로 나왔던 것만 쓴다 — 손으로 지어낸 예를 섞었더니 글자 모양 차이
(`/` 는 숫자보다 1px 위까지 올라간다)까지 잡혀서 헛되이 실패했다.

**검증** — 검사 도구 5종 전부 통과.

## 2026-09-06 — 앱이 한 번 조용히 죽었다 (그리고 그걸 쫓다가 더 죽였다)

배경에서 돌던 앱이 아무 말 없이 사라졌다. 남은 단서는 종료 코드 **139**
(세그폴트) 하나뿐이었다. 파이썬 예외도, 로그도 없었다.

### 잘못한 것 — `faulthandler` 를 붙였다가 앱을 죽였다

죽는 순간의 스택이라도 남기려고 `app/main.py` 에 `faulthandler.enable()` 을
붙였다. 그랬더니 **앱이 훨씬 자주 죽기 시작했다.** 붙인 도구가 원인이었다.

- faulthandler 켜고 최소 재현 6회 → **6회 다 세그폴트**
- faulthandler 끄고 같은 것 5회 → **5회 다 정상 종료**

윈도우에서 mpv 와 그래픽 드라이버는 **정상적으로 처리되는** 예외
(코드 `0xE24C4A02`)를 수시로 던진다. faulthandler 는 그것까지 치명적인 것으로
보고 프로세스를 끝낸다. 알아챈 계기는 덤프에 찍힌 자리였다 —
`pathlib.resolve()` 한복판, mpv 와 아무 상관 없는 파일 경로 코드였다.
**떨어진 스택이 사건 현장이 아니었다.** faulthandler 는 예외가 잡히면 모든
스레드의 스택을 찍기 때문에, 그 순간 각 스레드가 어디 있었는지가 나올 뿐이다.

되돌렸고, `app/main.py` 에 다시는 붙이지 말라고 이유와 함께 적어 뒀다.

### 원래의 죽음 — 원인을 못 찾았다. 다만 위험한 코드는 걷어냈다

한 번뿐이었고 재현되지 않는다. 지금 코드로 스트레스 검사를 돌리면 죽지 않는다.

- 탭을 진짜 마우스 클릭으로 마구 오가기 (3회 × 30바퀴) — 정상
- 비교 탭 재생 + 모드 전환 + 창 크기 변경 + 탭 이동을 섞어 20분 넘게 — 정상
- 검사 도구 5종 — 전부 통과

가장 의심스러웠던 코드는 걷어냈다. **탭을 누른 그 순간에 그 탭을 빼고 다시
끼우고 있었다**(`removeTab`/`insertTab`). 탭바는 아직 그 탭을 누르는 중인데
위젯이 사라지는 구조라 위험하다. 지금은 껍데기 페이지를 자리에 계속 두고
**안쪽 내용만** 바꾼다 — QTabWidget 은 아무것도 모르는 채로 있는다.
(따로 떼어 재현해 보려 했을 때는 안 죽었으므로, 이게 그 원인이었다고
단정하지는 않는다. 위험한 방식을 안 쓰는 쪽으로 바꿨을 뿐이다.)

**앞으로 또 조용히 죽으면** — 프로세스 안에서 예외를 가로채는 방식(faulthandler)
말고, 바깥에서 보는 방식(윈도우 오류 보고의 로컬 덤프)을 쓸 것.

## 2026-09-06 — 비교 탭이 재생 중에 위아래로 떨리던 것

**Consolas 에는 한글이 없다.** 그래서 한글이 섞이면 그 글자만 대체 글꼴로
그려지는데, 그쪽 글꼴이 2px 더 높다 — 그러면 라벨 높이가 통째로 2px 커진다.

비교 탭 카운터는 `A 00:00:02:00 · 60 / 120   B · 60 / 120` 이다가, 두 영상이
어긋나면 `(어긋남 +1)` 이 붙는다. 재생 중에는 이 꼬리표가 붙었다 떨어졌다
하므로 **라벨 높이가 17px ↔ 19px 로 계속 오르내렸다.** 카운터 줄은 영상과
같은 세로 배치에 있어서, 그 2px 이 영상 높이를 밀고 타임라인을 위아래로
움직였다. "뷰창이 움찔거린다"의 정체가 이것이었다.

재생 탭이 멀쩡했던 이유도 같은 계산에서 나온다 — 그 줄에는 높이 34px 로
고정된 프레임/타임코드 입력칸이 같이 있어서, 라벨이 2px 커져도 줄 높이를
못 바꾼다.

`widgets.lock_text_height()` 로 고쳤다. 숫자만 있는 글자와 한글이 섞인 글자를
둘 다 재서 큰 쪽으로 높이를 못박는다. 비교·트림 탭의 카운터에 걸었다.

```
못박기 끔 · 타임라인 y [531, 533] · 영상 높이 [481, 483]  -> 흔들림 2px
못박기 켬 · 타임라인 y [531]      · 영상 높이 [481]       -> 흔들림 없음
```

`smoke_compare.py` 에 `[E] 재생 중 화면이 위아래로 움찔거리지 않는가` 를 넣었다.
**카운터 글자가 실제로 바뀌었는지도 같이 확인한다** — 글자가 안 바뀌면 이 검사는
아무것도 지키지 못한 채 통과해 버리기 때문이다.

**검증** — 검사 도구 5종 전부 통과.

## 2026-09-06 — 반복 중 타임라인이 멈추던 것 · 탭을 늦게 만들기

### 구간 반복에서 영상은 도는데 타임라인만 멈춰 있었다

`_pending_frame` 이 범인이었다. seek 을 걸면 목표 프레임을 기억해 두고
`current_frame` 이 그 값을 돌려준다 (아직 도착 전이면 '가고 있는 프레임'이
기준이어야 하니까). 도착 판정은 `self.frame == target` 이었다.

**재생을 유지한 채 건 seek 에서는 이 판정이 성립하지 않는다.** 폴링이 30ms 인데
60fps 영상은 그 사이에 두 프레임쯤 지나간다 — 목표 번호를 그냥 건너뛴다.
그러면 도착을 영영 못 알아채고 `PENDING_MAX_POLLS`(20회 = **0.6초**)를 다 채운
뒤에야 풀린다. 그동안 `current_frame` 은 목표에 붙박여 있으니, 영상은 도는데
타임라인만 멈춰 보였다.

재생 중에는 **출발점보다 목표에 더 가까워졌으면 도착**으로 본다
(`MpvWidget._seek_arrived`). 정지 상태의 프레임 이동은 그대로 정확히 일치할
때만 도착이다 — 한 칸도 어긋나면 안 되는 자리라서.

`tools/smoke_range.py` 에 "같은 프레임 번호가 연달아 몇 번 나오는가"를 재는
검사를 넣었다. **최대 20회 연속(0.6초) → 2회 연속(80ms).**

### 비교·트림 탭을 처음 열 때 만들도록

켜는 순간 mpv 인스턴스 4개(재생 1 · 비교 2 · 트림 1)를 다 만들고 있었다.
탭을 처음 누를 때 만들도록 바꿨다.

| | 전 | 후 |
|---|---|---|
| 창 뜨기까지 | 6409 ms | **2033 ms** |
| 시작 시 mpv | 4개 | 1개 |

`self.compare` · `self.trim` 을 프로퍼티로 두어서, 처음 건드리는 쪽이 만들게
했다 — 검사 도구들(`smoke_compare` 등)이 세 탭을 전제로 쓰고 있어서 그쪽 코드를
한 줄도 안 고치고 넘어갈 수 있었다. 탭 자리에는 껍데기 위젯을 넣어 두고,
`tabBarClicked`(= 바뀌기 **전**)에 진짜 탭으로 갈아 끼운다. 그래야 빈 자리가
스치지 않는다. 안 만든 탭의 설정은 `_apply_compare_settings` ·
`_apply_trim_settings` 로 미뤄 뒀다가 만들 때 넣어 준다.

### 창 크기 조절 — 여기까지 파 봤고, 우리 코드가 아니었다

두 번 지적받아서 끝까지 재 봤다. **원인이라고 짚을 만한 게 우리 쪽에 없다.**

| 무엇을 바꿔 봤나 | 리사이즈 |
|---|---|
| 지금 그대로 | 145 ms |
| 테마(QSS)를 아예 안 입힘 | 177 ms (오히려 느림) |
| mpv 4개 → 1개 (탭 늦게 만들기) | 162 ms (그대로) |
| 프레임리스 끄고 윈도우 창틀로 | 173 ms (그대로) |
| DPI 반올림 정책 1.5 / 2.0 / 1.0 | 149 / 156 / 140 ms (그대로) |

비용이 어디 있는지도 갈라 봤다:

| | |
|---|---|
| 창 전체 다시 그리기 | 15 ms |
| 레이아웃 다시 계산 | 0.02 ms |
| **크기가 실제로 바뀔 때** | **145 ms** |
| 같은 크기로 resize (무시됨) | 5.5 ms |

그리기도 레이아웃도 아니고 **창 크기 변경 그 자체**가 비싸다. 위젯을 하나씩
숨겨 가며 재면 172 → 100 → 49ms 로 조금씩 줄 뿐 범인이 한 곳에 없고, 위젯을
다 숨긴 빈 창도 49ms 다 (아무것도 없는 Qt 창은 11ms). 위젯 수에 대체로
비례하는 Qt/Windows 쪽 비용으로 보인다.

**목업 작업 때문에 느려진 게 아니라는 것은 확실하다** — 테마를 통째로 뗀 같은
창이 오히려 더 느리다. 더 줄이려면 QTabWidget 을 직접 만든 스택으로 바꾸는
식의 실험이 남아 있는데, 효과가 불확실해서 손대지 않았다.

**검증** — 검사 도구 5종 전부 통과 (재생·비교·트림·설정·구간).

## 2026-09-06 — 구간 재생·반복, 그리고 "정확 컷이 안 열린다"

### "정확히 자르기 결과가 코덱 오류로 안 열린다" — 파일은 멀쩡했다

윈도우 기본 플레이어가 `0xC00D5212 · 지원되지 않는 Unknown 형식` 을 냈다.
확인해 보니 **파일은 정상이고 코덱이 ffv1** 이었다.

```
cut_precise.mkv : 코덱=ffv1  픽셀=yuv420p     ← 정확 컷 (기본 인코더)
cut_lossless.mkv: 코덱=h264  픽셀=yuv420p     ← 무손실 컷 (원본 그대로 remux)
```

ffv1 은 무손실이라 "정확하게 자르되 화질은 그대로"라는 정확 컷의 목적에 맞는
기본값이지만(4단계 결정), **윈도우 기본 플레이어가 ffv1 을 모른다.** 우리
smoke_trim 검사는 이 파일이 원본과 픽셀 단위로 같다는 것까지 확인하고 있었다 —
잘못 만든 게 아니라 재생기가 못 여는 것이다.

기본값을 바꾸지 않았다. 대신 **누르기 전에 알려 주는** 이 탭의 방식(4단계의
"예고" 패턴)을 그대로 따랐다. 미리보기 줄에 한 줄이 붙는다:

> ※ 정확 컷 결과(ffv1)는 PlayerX·VLC 에서는 열리지만 윈도우 기본 플레이어로는
> 안 열립니다. 어디서나 열리는 파일이 필요하면 인코더를 H.264 로 바꾸세요.

내보내기가 끝난 뒤 상태줄에도 같은 말이 붙는다. H.264 로 바꾸면 실제로 어디서나
열리는 파일이 나오는지도 확인했다 (`libopenh264` · 96~278 · 1.0MB · h264/yuv420p).
이 ffmpeg 빌드에 실제로 있는 H.264 인코더는 `libopenh264` · `h264_nvenc` ·
`h264_qsv` · `h264_amf` 네 가지다.

### 고른 클립만 재생 · 구간 반복

목록에서 클립을 고르고 재생하면 그 구간만 돌게 했다. 클립 목록 아래에
체크 두 개가 생겼다 — **선택 구간만 재생** · **구간 반복** (둘 다 기본 켜짐,
설정에 저장된다).

- 재생을 누를 때 구간 밖이거나 이미 끝이면 IN 부터 다시 튼다.
- 구간 끝에 닿으면 반복이 켜져 있으면 IN 으로 돌아가고, 꺼져 있으면 OUT 에서 멈춘다.
- **가두는 건 재생뿐이다.** 타임라인을 손으로 끄는 건 구간 밖으로도 된다 —
  검수 중에 구간 바깥을 잠깐 확인하는 일이 흔해서 그렇게 뒀다.

되돌아갈 때 `seek_pending` 을 본다 (`MpvWidget` 에 새로 붙인 속성). 방금 건
점프가 도착하기 전에 또 걸면 같은 자리를 계속 다시 찾는다.

검사는 `tools/smoke_range.py` 로 새로 만들었다. `_enforce_range()` 를 직접
부르는 게 아니라 **실제로 재생시켜 놓고 프레임 번호를 계속 받아 적는다** —
폴링에 제대로 연결됐는지, mpv 가 정말 그 자리에 서는지가 확인하려는 것이라서다.

```
[A] 반복 켜짐  가장 낮은 100 · 가장 높은 159 · 5회 반복       (구간 100~160)
[B] 반복 꺼짐  OUT 에서 스스로 멈춤 · 멈춘 자리 160
[C] 구간 재생 끔  가장 높은 296 — 구간을 지나 계속 재생됨
[D] 정지 상태에서 500번 프레임으로 이동 가능 (타임라인은 안 가둔다)
```

### 곁가지

- 체크박스가 켜져도 파란 사각형만 차고 **체크 표시가 없었다.** 테마에서
  `QCheckBox::indicator` 를 직접 칠하고 있었기 때문이다. 그 규칙을 지우고
  Fusion 이 팔레트를 보고 그리게 두니 체크 표시가 돌아왔다.

**검증** — 검사 도구 5종 전부 통과 (재생·비교·트림·설정·구간).

## 2026-09-06 — 느려진 것 되돌리기 (목업 반영 직후)

목업을 입힌 뒤 "버벅거린다 · 타임라인이 늦게 따라온다 · 창 크기 조절이 느리다 ·
비교 탭이 깨진다"는 보고가 있었다. 추측하지 않고 다 쟀다.

### 잰 값 (고치기 전 → 고친 뒤)

| 항목 | 전 | 후 |
|---|---|---|
| 타임라인 한 번 그리기 | 10.24 ms | **0.27 ms** |
| `_sync()` (폴링 1회분) | 0.06 ms | 0.01 ms |
| `player._refresh()` | 0.13 ms | 0.03 ms |
| 창 리사이즈 | 197 ms | 168 ms |

타임라인은 재생 중 초당 30번 그린다. 10ms × 30 = **CPU 한 코어의 30%를
타임라인 하나가 쓰고 있었다.** "기본적으로 버벅거린다"의 정체가 이거였다.

### 원인 1 — 전체 선택자 `QWidget { background: transparent; }`

테마를 만들 때 글자색·글꼴을 한 번에 주려고 넣은 규칙인데, 이것 하나 때문에

* 모든 위젯의 그리기를 스타일시트 엔진이 떠맡고,
* `transparent` 라서 **위젯을 다시 그릴 때마다 그 뒤의 조상까지 같이 그린다.**

타임라인만 다시 그리면 될 것을 창 전체를 다시 그리고 있었다. 규칙을 지우고
글자색은 팔레트로, 글꼴은 `app.setFont()` 로 옮겼다. 화면은 그대로다.
**이것만으로 타임라인 그리기가 38배 빨라졌다.**

### 원인 2 — 눈금과 글자를 매번 다시 그렸다

타임라인의 눈금 수십 개와 시각 글자 여덟 개는 크기가 바뀌지 않는 한 늘 같은
그림이다. 픽스맵에 한 번 그려 두고(`_static_layer`), 움직이는 것(재생 위치·
IN/OUT·인덱싱 진행률)만 그 위에 얹는다. `WA_OpaquePaintEvent` 도 같이 켰다.

### 원인 3 — 끄는 동안 seek 을 그대로 다 흘렸다

"타임라인을 옮겨도 한참 뒤에 바뀐다"의 원인. 마우스는 초당 수백 번 움직이는데
그때마다 mpv 에 seek 을 보내니 요청이 쌓여서, 손을 뗀 뒤에도 계속 따라왔다.

* **표시와 seek 을 분리했다.** 재생 위치 표시는 손을 따라 즉시 움직이고,
  seek 은 40ms 간격으로만 보낸다. 손을 뗀 자리는 간격과 무관하게 반드시 보낸다.
* 프레임 번호가 실제로 바뀔 때만 보낸다 (같은 프레임에 여러 번 보내지 않는다).

### 원인 4 — 비교 탭이 리사이즈 때 깨졌다

`CompareView` 는 resizeEvent 마다 네이티브 창 두 개를 옮기고 마스크를 다시
씌운다. 창을 끌면 초당 수백 번 들어오니 그림이 찢어진다. 배치를 30ms 로 묶고,
안 보이는 탭이면 아예 건너뛴다 (`showEvent` 에서 한 번에 맞춘다).

### 곁가지

- 디코더 이름(`hwdec-current`)을 폴링마다 물어보고 있었다 (속성 조회 2회 ×
  플레이어 4개 × 초당 33회). 0.25초에 한 번으로 줄였다.
- `QLineEdit.setText` 는 값이 같아도 커서를 되돌리고 다시 그린다. 프레임/타임코드
  칸이 폴링마다 그러고 있었다 — 값이 바뀔 때만 넣는다.
- 창 가장자리 커서를 마우스가 움직일 때마다 다시 지정하고 있었다 — 바뀔 때만.

### 창 크기 조절은 아직 느리다 (그리고 이건 원래 그랬다)

197 → 168ms 로 줄긴 했지만 여전히 느리다. **테마 때문이 아니다** — 테마를 아예
안 입힌 같은 창이 오히려 177ms 다. 재 보면 비용은 mpv 인스턴스 수를 따라간다:

| mpv 인스턴스 | 리사이즈 (테마 없는 맨 창) |
|---|---|
| 0개 | 14.7 ms |
| 1개 | 49.8 ms |
| 2개 | 69.4 ms |
| 4개 | 93.1 ms |

지금은 앱을 켜는 순간 **네 개**를 다 만든다 (재생 1 · 비교 2 · 트림 1).
탭을 처음 열 때 만들도록 바꾸면 보통 사용에서 1개로 줄고 리사이즈도 그만큼
싸진다. 설정 저장/복원과 검사 도구가 세 탭을 전제로 하고 있어서 손이 좀 가는
작업이라, 별도로 남겨 둔다.

**검증** — 검사 도구 4종 전부 통과 (재생·비교·트림·설정). 화면도 그대로다.

## 2026-09-06 — 화면 목업 반영 (뒤늦게)

**왜 이 작업이 따로 생겼나.** 목업(`docs/mockups/mockup-20260905-1909.png`)은 계획서에
그림으로만 붙어 있었고 1~5단계 어디에서도 UI 코드로 옮겨진 적이 없었다. 기능은 다 됐는데
화면은 윈도우 기본 테마에 기본 위젯 그대로였다 — 테마 파일이 하나도 없었고, 위젯 몇 개에
`color: #888888` 같은 임시 색만 박혀 있었다. **다음부터는 단계마다 목업과 실제 화면을
나란히 놓고 확인해야 한다.**

**만든 것**

- `app/theme.py` — 목업에서 뽑은 색 토큰(`C`)과 앱 전체 QSS 하나. 위젯 코드는 색을
  들고 있지 않고 `objectName` 만 정한다. `Fusion` 스타일을 쓰는 이유는 윈도우 기본
  스타일이 콤보 화살표·체크 표시 같은 부분을 QSS 와 무관하게 시스템 테마(밝게)로
  그리기 때문이다.
- `app/icons.py` — 아이콘을 파일이 아니라 QPainter 로 그린다. 색을 인자로 받으므로
  활성/비활성/강조를 그림 하나로 내고, PyInstaller 로 챙길 리소스도 안 늘어난다.
- `app/widgets.py` — 목업에만 있던 조각들. 눈금·시각·IN/OUT 마커가 함께 있는
  `TimelineBar`(QSlider 로는 마커를 얹을 자리가 없다), 아이콘·이름·단축키가 쌓인
  `TransportButton`, 카드형 `InfoPanel`, `FieldBox`(프레임/타임코드 입력), `StatusStrip`.
- `app/chrome.py` — 목업의 창 위쪽은 `PlayerX │ 파일명 … ─ □ ✕` 한 줄이라
  `FramelessWindowHint` 로 창틀을 끄고 헤더를 위젯으로 그린다. 옮기기·크기 조절은
  `QWindow.startSystemMove()` / `startSystemResize()` 에 넘긴다 — 좌표를 직접 계산하면
  스냅·다중 모니터·DPI 가 섞였을 때 어긋난다.
- `app/timecode.py` — `parse_timecode()`. 타임코드 입력칸이 `HH:MM:SS:FF` 와
  앞자리 생략(`MM:SS:FF`), 그냥 프레임 번호를 다 받는다.

**세 탭 모두 같은 언어로.** 비교·트림 탭도 같은 타임라인·같은 조작 버튼을 쓴다.
탭을 옮겨도 버튼이 같은 자리·같은 크기라 손이 기억한 자리를 그대로 누르게 된다.

### 만들면서 잡은 것

- **아이콘이 4분의 1만 그려졌다.** `devicePixelRatio` 를 준 픽스맵의 그리기 좌표는
  이미 논리 좌표인데 거기에 dpr 을 또 곱해서 그림이 두 배로 커져 잘렸다.
  스케일을 `size / 24` 로 고쳤다.
- **커스텀 위젯의 배경·테두리가 안 그려졌다.** QWidget 을 상속한 위젯은
  `Qt.WA_StyledBackground` 를 켜야 스타일시트의 배경을 그린다. 카드·헤더·상태줄이
  전부 바탕색과 똑같이 나오던 원인이었다.
- **헤더의 파일명이 재생 탭에서만 바뀌었다.** 창이 파일을 여는 경로(`open_path`)에만
  붙여 놨더니 비교·트림 탭의 '열기…' 버튼으로 연 파일은 반영되지 않았다.
  네 플레이어의 `file_loaded` 를 듣게 바꿔서 어느 경로로 열든 따라간다.
- **영상 위에 위젯을 못 얹는다.** 목업은 영상 모서리에 배율·색공간 표시가 떠 있는데,
  mpv 는 네이티브 자식 창이라 윈도우에서 항상 형제 위젯보다 위에 그려진다.
  그 표시를 영상 바로 위 띠로 옮겼다.

### 계획서·목업과 다르게 한 것

- **메뉴 표시줄을 없애고 헤더의 ☰ 로 옮겼다.** 목업의 창 위쪽은 헤더 한 줄뿐이다.
  단축키가 걸린 항목은 창에도 직접 등록해야(`addAction`) 메뉴를 열지 않아도 듣는다.
- **재생 탭에 IN/OUT 찍기를 넣었다** (목업에 있다). 여기서 찍은 구간은 트림 탭으로
  넘어갈 때 그대로 이어진다 (`MainWindow._hand_over_marks`).
- **`QStatusBar` 대신 `StatusStrip`.** 창틀을 직접 그리느라 QMainWindow 의 상태
  표시줄이 프레임 밖으로 나가서다. 이름을 `showMessage` 로 맞춰 뒀으므로 부르는 쪽
  코드는 그대로다.

### 만들면서 잡은 것

**1. PyInstaller 6 은 번들 내용물을 exe 옆이 아니라 `_internal\` 에 넣는다.** 5.x 는
exe 옆이었다. 스펙에서 `(src, '.')` 로 지정해도 `_internal\` 로 간다. 우리 로더들은
frozen 일 때 `sys.executable` 의 부모만 보고 있었다. → **exe 옆 → exe 옆 `vendor\` →
`sys._MEIPASS`** 순으로 찾게 고쳤다. exe 옆을 먼저 보는 게 중요하다 — ffmpeg 을 나중에
GPL 빌드로 바꾸고 싶으면 번들을 건드리지 않고 exe 옆에 떨어뜨리면 그게 이긴다.

**2. 디코더를 바꾼 직후에 읽으면 이전 값이 나온다.** mpv 는 디코더를 그 자리에서
갈아 끼우지 않고 다음 프레임에 다시 만든다. `set_hwdec()` 안에서 곧바로
`hwdec-current` 를 읽었더니, **되는 디코더(d3d11va)로 되돌렸는데도 "이 PC 에서 안 된다"고
표시했다.** 정보 패널이 거짓말을 한 것이다.
→ 값 스냅샷을 버리고 `_refresh()`(30ms 폴링)가 매번 다시 읽게 했다. 메뉴를 고른 뒤에는
0.7초 뒤에 패널을 새로 그린다. 이제 nvdec 만 "안 돼서 소프트웨어로"라고 나온다
(이 PC 에 NVIDIA GPU 가 없으니 맞는 말이다).

**3. mpv 의 `hwdec` 는 리스트로 돌아온다.** 콤마로 여러 개를 줄 수 있는 옵션이라
`['nvdec']` 이 정보 패널에 그대로 찍혔다. → `_as_text()` 로 정리.

**4. 키프레임 간격의 초 계산이 틀렸다.** `프레임 수 x 대표 간격` 으로 냈더니 60fps
60프레임이 **1.02초**로 나왔다. mkv 의 1ms 타임베이스 양자화(16/17ms)가 누적된 것이다.
→ PTS 표에서 두 키프레임의 시각을 직접 빼서 잰다. 1.00초.

**5. 검증 스크린샷 도구에 QApplication 이 없었다.** `verify_package.py` 는 GUI 앱이
아닌데 화면을 캡쳐한다. `QGuiApplication.primaryScreen()` 이 None 이라 터졌다.
→ 최소한의 `QGuiApplication` 을 세워 둔다.

**6. 안 쓰는 Qt DLL 이 딸려 왔다.** 스펙의 `excludes` 는 파이썬 모듈만 막는다.
QML 스택(Qt6Quick·Qt6Qml, 11MB)은 의존 그래프를 타고 그대로 들어왔다.
→ `a.binaries` 에서 직접 덜어 냈다. 사실 필요했던 것이면 앱이 안 켜지는데,
`verify_package.py` 가 묶은 결과물을 실제로 실행해 보므로 그건 바로 잡힌다.

### 계획서와 다르게 한 것

- **설정 창을 만들지 않고 메뉴로 했다.** 계획서가 "혼자 쓰는 도구라 설정 화면도
  최소로"라고 못박아 뒀고, 고를 게 세 가지뿐이다. 라디오 메뉴면 지금 무엇이 켜져
  있는지도 같이 보인다.
- **`--selftest` 를 만들었다.** 계획에 없던 것이다. 묶은 앱이 안 켜질 때 이유를 알
  방법이 없어서(콘솔이 없다) 앱 자신이 점검하게 했다. 5-6 검증도 이것 위에 서 있다.
- **PNG 시퀀스를 ffmpeg 이 아니라 PyAV 로 뽑는다.** 낱장 캡쳐와 **같은 그림**이
  나와야 하기 때문이다. ffmpeg 으로 뽑으면 색 변환 규칙이 두 군데로 갈라진다.
- **정보 패널에 "하드웨어 디코딩"을 고른 값이 아니라 실제 값으로 적는다.**
  계획서는 "on/off · 디코더 선택 UI"까지만 적혀 있었는데, mpv 가 조용히 물러나는
  이상 고른 값을 적는 건 거짓말이 된다.

### 만들면서 잡은 것

**1. LGPL 빌드에는 x264 가 없다.** 계획서 라이선스 표의 판단대로 LGPL 빌드를 받았는데
(`--disable-libx264 --disable-libx265`), 그러면 "정확 컷(재인코딩)"에 쓸 H.264
인코더가 소프트웨어로는 `libopenh264` 뿐이다. → **인코더를 코드에 박지 않고 런타임에
탐지한다.** `ffmpeg -encoders` 를 읽어서 이 빌드에 실제로 있는 것만 UI 에 내놓는다.
GPL 빌드를 받으면(`tools/fetch_ffmpeg.py --gpl`) x264 가 목록에 저절로 나타난다.
**기본값은 `ffv1`(무손실)로 뒀다** — "정확 컷"의 목적은 IN 을 정확히 맞추는 것이지
화질을 깎는 게 아니다. 화질까지 지키는 선택지가 있으면 그게 기본이어야 한다.

**2. `-ss` 를 `-i` 앞에 두면 `-to` 의 기준이 바뀐다.** 앞에 두는 건 필수다(뒤에 두면
파일 처음부터 훑어서 긴 파일이 몇 분씩 걸린다). 그런데 그러면 `-to` 가 **잘라 낸 뒤의
시간축** 기준이 돼서 엉뚱한 데서 끝난다. → `-to`(절대 시각) 대신 `-t`(길이)를 쓴다.

**3. 무손실 컷의 시작 시각을 키프레임 시각 그대로 주면 한 칸 앞으로 샐 수 있다.**
ffmpeg 은 `-ss` 시각 *이전*의 키프레임을 찾는데, 프레임 시작은 경계라서 부동소수점에
따라 어느 쪽으로도 해석된다. → 그 프레임이 떠 있는 구간 **안쪽**(다음 프레임까지
간격의 1/4)을 겨냥한다. 2단계 seek 에서 쓴 것과 같은 요령이다.

**4. 검증 스크린샷에 편집기 창이 찍혔다.** Windows 는 포그라운드가 아닌 프로세스가
`SetForegroundWindow` 로 앞에 나서는 걸 막아서, `raise_()`·`activateWindow()` 로는
안 올라온다. → `SetWindowPos(HWND_TOPMOST)` 로 '항상 위'를 준다. **그런데 여기서 두 번
더 걸렸다:**
  - `ctypes.windll.user32` 를 argtypes 없이 부르면 인자가 c_int(32비트)로 넘어가
    **64비트 창 핸들이 잘린다.** 조용히 아무 일도 안 일어난다.
  - 무조건 `ShowWindow(SW_RESTORE)` 를 부르면 **최대화까지 풀려서** 창이 작아진 채
    찍힌다. 최소화됐을 때만 불러야 한다.
  `tools/screengrab.py` 로 빼서 세 스모크 도구가 같이 쓴다.

### 계획서와 다르게 한 것

- **`O` 를 누르면 그 자리에서 클립이 된다.** 계획서는 마킹과 목록 추가를 따로 적어
  뒀는데, 한 구간에 키를 세 번 눌러야 하면 실제로 안 쓰게 된다. IN 이 이미 있는
  상태의 `O` 는 "구간 완성"으로 본다. (IN 없이 `O` 만 누르면 OUT 만 기억해 둔다)
- **클립 목록 표에 '무손실 시작' 칸을 뒀다.** 4-9 는 "가장 가까운 키프레임 위치를
  UI 에 표시"였는데, 선택한 클립 하나만 보여 주는 것보다 **목록 전체에서 어느 구간이
  많이 밀리는지 한눈에 보이는 게** 낫다. 5프레임 넘게 밀리면 주황색으로 칠한다.
- **영상을 열 때 옆에 있는 `.clips.json` 을 자동으로 읽는다.** 트림은 여러 번에 걸쳐
  하는 작업이라, 다시 열 때마다 불러오기를 눌러야 하면 목록이 있으나 마나다.
- **탭을 트림으로 옮기면 재생 탭에서 보던 파일을 이어받는다.** 인덱스가 캐시돼 있어
  즉시 열린다. 같은 영상을 탭마다 다시 고르는 건 창 하나짜리 도구에서 할 일이 아니다.
- **`I`·`O`·`[`·`]` 를 다른 탭에서 누르면 "트림 탭의 키"라고 알린다.** 아무 반응이
  없으면 고장으로 보인다.

### 만들면서 잡은 것

**1. 와이프는 위젯을 줄이면 안 된다.** mpv 는 네이티브 창 안에 직접 그려서, 위젯을
반으로 줄이면 영상도 반으로 **축소**된다 — 그건 와이프가 아니라 그냥 작은 화면 두 개다.
그래서 두 위젯을 **둘 다 전체 크기로 겹쳐 놓고** `setMask()` 로 보이는 영역만 잘라 낸다.
마스크는 크기를 안 건드리고 잘라내기만 하므로 두 영상의 배율과 위치가 정확히 겹친다.
설계를 정하기 전에 실험으로 먼저 확인했다 (내용이 확연히 다른 두 영상을 겹쳐 놓고
스크린샷).

**2. 경계선을 위젯으로 만들면 영상에 가린다.** Windows 에서 네이티브 자식 창(mpv)은
언제나 일반 위젯보다 위에 그려진다. `raise_()` 도, 경계선을 네이티브 창으로 만들어
보는 것도 소용이 없었다. → **경계선을 그리지 않고 "안 그리는 틈"으로 만든다.**
두 마스크 사이에 6px 틈을 남기면 그 자리는 어느 자식도 덮지 않으므로, 부모(CompareView)의
`paintEvent` 가 거기 노란 선을 그리고 **마우스 이벤트도 그리로 들어온다**. 끌기까지
공짜로 해결됐다.

**3. 차분 모드에서 한 프레임씩 넘기면 매번 GOP 를 다시 풀었다.** `FrameCapturer` 가
호출마다 키프레임으로 seek 했기 때문이다. 60 프레임을 순서대로 꺼내는 데 683ms.
→ 직전에 꺼낸 프레임보다 60 프레임 이내로 앞이면 탐색을 건너뛰고 이어서 디코딩한다.
**26ms 로 줄었다 (26.6배).** 결과가 탐색 경로와 바이트 단위로 같은지, 역방향 이동도
여전히 맞는지 확인했다.

**4. 차분 요청이 쌓이면 한참 뒤처진 그림이 계속 올라온다.** 프레임을 빠르게 넘기면
요청이 큐에 밀린다. → 계산이 도는 중이면 새 요청을 큐에 넣지 않고 "더러움" 표시만 해 두고,
끝났을 때 **한 번만** 다시 요청한다. 중간 요청은 버린다 — 어차피 '지금 상태'만 중요하다.

**5. 재생/정지를 토글로 다루면 두 인스턴스가 반대로 갈라진다.** 한쪽이 이미 어긋나
있으면 토글이 둘을 정반대 상태로 만든다. → `MpvWidget.set_paused(bool)` 를 만들어
비교 탭은 항상 명시적으로 지정한다.

**6. 재생 중 프레임 잠금을 매 폴링마다 걸면 B 가 계속 끊긴다.** A 의 `state_changed`
는 30ms 마다 온다. 거기서 매번 B 를 seek 하면 재생이 성립하지 않는다. → 멈춰 있을
때만 즉시 동기화하고, 재생 중에는 500ms 주기 타이머가 **허용치(2프레임)를 넘을 때만**
끌어온다. `seek_to_frame(keep_playing=True)` 를 추가한 이유다 — 재생 중에 매번
멈췄다 켜면 그림이 튄다.

### 계획서와 다르게 한 것

- **차분만 mpv 가 아니라 PyAV 로 그린다.** 화면에 그려진 픽셀을 빼면 창 크기·GPU 의
  색 변환이 차이에 섞여서, 인코딩 차이인지 렌더링 차이인지 구분할 수 없다. 2단계
  캡쳐와 같은 이유·같은 경로(원본 재디코딩)를 쓴다. 그래서 차분 모드에서는 mpv 위젯을
  숨기고 계산한 그림을 대신 띄운다.
- **해상도가 다른 두 영상도 차분할 수 있게 했다.** 계획서에는 없던 경우인데, 실제로
  해 보면 자주 마주친다(다운스케일 인코딩 비교). B 를 A 크기로 늘려서 빼되,
  **"리샘플링 오차가 섞여 있습니다"를 화면에 같이 적는다.** 조용히 늘리면 차분 숫자를
  믿을 수 없게 된다.
- **차분에 PSNR·최대·평균·다른 픽셀 비율을 같이 낸다.** 계획서는 "NumPy 연산"까지만
  적혀 있었는데, 증폭된 그림만 보면 "차이가 크다/작다"를 말할 수 없다. 그림은 보라고
  증폭한 값이고 숫자는 증폭 전 실제 값이다 — 둘을 섞지 않게 코드와 UI 둘 다에 적어 뒀다.
- **단축키가 탭을 따라간다.** 1단계에는 재생 탭 하나뿐이라 위젯에 직접 묶여 있었다.
  두 탭이 같은 이름의 메서드(`step_frames`·`toggle_pause`·`goto_*`·`capture_current_frame`)를
  갖게 하고 `MainWindow` 가 현재 탭으로 넘긴다.
- **B 의 소리를 끈다.** 두 영상이 같이 울리면 아무것도 못 듣는다.
- **탭을 옮기면 반대쪽 탭은 멈춘다.** 안 보이는 영상이 계속 도는 건 이득이 없다.

- **차분은 A·B 양쪽 인덱스가 다 있어야 돈다.** 인덱싱 중에는 안내 문구가 뜬다.

### 만들면서 잡은 것

**1. PyAV 의 `reformat()` 은 src/dst 레인지가 같으면 색 설정을 건너뛴다.**
`VideoReformatter._reformat()` 이 `src_colorspace != dst_colorspace or src_color_range != dst_color_range`
일 때만 `sws_setColorspaceDetails()` 를 부른다. 그래서 **풀레인지 소스를 풀레인지로
뽑을 때 우리가 준 설정이 통째로 무시된다** — swscale 기본값(limited 소스 가정)으로
변환돼 명암이 틀어진다. 실측으로 확인했다(Y=U=V=128 을 넣으면 `src=pc` 를 줘도
`src=tv` 와 똑같이 130 이 나온다). → 캡쳐는 `reformat()` 대신 **ffmpeg `scale` 필터그래프**를
쓴다. `in_range`/`out_range`/`in_color_matrix`/`out_color_matrix` 를 명시로 박으면
구멍이 없다. 필터 쪽은 `in_range=tv` 130, `in_range=pc` 128 로 제대로 갈린다.

**2. Pillow 은 16bit RGB PNG 를 못 쓴다.** 계획서 기술스택에는 "이미지 저장 = Pillow"
라고 적어 뒀는데, Pillow 의 16bit 지원은 그레이스케일(`I;16`)뿐이다. 10bit 소스를
16bit PNG 로 저장하는 게 2단계 요구사항이라 그대로는 안 된다. → **FFmpeg 의 png
인코더**로 인코딩한다(`CodecContext.create("png","w")`, `pix_fmt=rgb48be`). 인코더가
내놓는 패킷이 그대로 완결된 PNG 파일이다. PyAV 를 이미 쓰고 있으니 의존성도 안 는다.
Pillow 은 venv 에서 지웠다.

**3. 검증용 VFR 파일이 VFR 로 안 만들어졌다.** `add_stream("ffv1", rate=30)` 만 하면
인코더 time_base 가 1/30 이 돼서, 우리가 준 ms 단위 PTS 가 프레임 단위로 반올림된다.
서로 다른 두 프레임의 PTS 가 같은 값(133ms)으로 뭉개져서 인덱스가 90개가 아니라
73개를 봤다. → `stream.codec_context.time_base` 를 직접 박았다.

**4. 검증용 파일을 BT.601 로 인코딩해 놓고 BT.709 라고 태깅했다.** (3)을 고치고도
"캡쳐한 그림이 4번 프레임"처럼 색이 계속 어긋났다. 원인은 캡쳐가 아니라 생성기 쪽 —
`reformat(format=...)` 에 아무것도 안 주면 swscale 기본 매트릭스로 변환하는데,
컨테이너에는 709 라고 적고 있었다. 캡쳐가 (파일 말대로) 709 로 되돌리니 원본과
다른 색이 나온 것. → 생성기도 변환과 태그를 같은 값으로 명시한다. **캡쳐 코드는
처음부터 맞았고, 검증 기준선이 틀렸던 경우다.**

**5. 16bit RGB 를 8bit YUV 로 내리면 swscale 이 디더링을 건다.** 단색 프레임이
얼룩져서 "이 픽셀이 몇 번 프레임인가"를 못 읽었다. → 생성기가 목표 비트 뎁스에 맞춰
RGB 를 만들고, 판독기는 픽셀 하나가 아니라 **한 행의 중앙값**을 본다.

**6. 8bit limited 레인지 왕복은 ±1 이 뜬다.** 219 단계만 쓰니 되돌릴 때 오차가 낀다.
프레임 번호를 눈금 1 로 심었더니 89번이 345번(상위 바이트가 0→1)으로 읽혔다.
→ 64진수 두 자리를 **눈금 4로 벌려** 심는다. ±1 오차가 반올림에 흡수된다.

> (3)~(6)은 전부 **검증 도구 쪽 버그**였다. 앱 코드는 안 고쳤다. 그래서 검증이
> 자기 자신을 확인하지 않도록, "맨 앞부터 순차 디코딩한 n 번째 프레임"과 캡쳐 결과를
> **평면 바이트 단위로** 비교하는 독립 경로(D1/D2)를 따로 뒀다.

### 계획서와 다르게 한 것

- **캡쳐도 백그라운드 스레드로 돌린다.** 계획서에는 인덱싱만 스레드로 적혀 있었는데,

## 2026-09-05 — 1단계: 재생과 프레임 이동

계획서 9절의 1단계. 범위는 계획서대로 **열기 · 재생/정지 · 프레임 이동 · 프레임 번호 표시**로
고정했다. 캡쳐는 넣지 않았다.

**만든 것**

- `app/mpv_loader.py` — `libmpv-2.dll` 을 찾아 `os.add_dll_directory()` 로 등록한 뒤 `import mpv`.
  계획서가 "가장 시간 잡아먹는 구간"으로 지목한 곳이라 제일 먼저 했다.
  DLL 이 없으면 어디에 뭘 넣으라는 대화상자를 띄운다.
- `app/timecode.py` — 프레임 번호 ↔ 시각 ↔ 타임코드 변환. **프레임 정확도의 핵심이 여기 다 있다.**
- `app/player.py` — libmpv 를 Qt 위젯의 `winId()` 안에 박아 넣은 재생 표면.
  프레임 이동, 절대 seek, mpv 설정.
- `app/main_window.py` — 재생 탭 (영상 · 타임라인 · 프레임 카운터 · 파일 정보 패널),
  메뉴, 단축키, 드래그앤드롭.
- `app/main.py`, `run.py` — 진입점.
- `tools/test_timecode.py` — 변환 계산 단위 테스트 (파일 없이 즉시).
- `tools/verify_frame_accuracy.py` — 창 없이 libmpv 로 실제 seek 을 걸어 목표 프레임에
  도착하는지 확인. mpv 자체 `frame-back-step` 과 나란히 비교한다.
- `tools/smoke_gui.py` — GUI 를 띄우고 `QTest.keyClick` 으로 진짜 키 이벤트를 보내
  단축키 → 이동 → 카운터까지 통째로 확인. 단계마다 스크린샷을 남긴다.
- `testdata/` — 프레임 번호가 그림에 박힌 검증용 영상 3개 (60fps mkv, 120fps mkv, 23.976fps mp4).
- `vendor/libmpv-2.dll` — mpv v0.41.0-1023 (shinchiro 빌드, 120MB). `.gitignore` 에 넣었다.
- `README.md`, `requirements.txt`, `.gitignore`

### 만들면서 잡은 것 — 프레임이 한 칸씩 밀리던 두 가지 원인

처음 검증을 돌렸을 때 27건이 실패했다. 원인은 둘 다 내 계산 쪽이었다.

**1. mpv 의 exact seek 은 목표 시각 '이후' 첫 프레임으로 간다.**
그 시각을 *포함하는* 프레임이 아니다. 처음에는 프레임 한가운데 `(n+0.5)/fps` 를 겨냥했는데,
그러면 항상 `n+1` 에 도착한다. 프레임 시작보다 살짝 앞 `(n-0.25)/fps` 를 겨냥하도록 바꿨다
(`timecode.SEEK_LEAD`).

**2. PTS 는 양자화돼 있다.**
mkv 의 기본 타임베이스는 1ms 라서 60fps 영상의 599번 프레임 PTS 가 9.98333… 이 아니라
**9.983** 으로 저장된다. `floor(time × fps)` 로 프레임 번호를 내면 598 이 나온다.
반올림으로 바꿨다 (`timecode.frame_at_time`). 이 두 케이스는 `tools/test_timecode.py` 에
회귀 테스트로 박아 뒀다.

### 계획서와 다르게 한 것

- **뒤로 이동을 1단계에서 이미 절대 seek 으로 만들었다.** 계획서는 2단계 작업으로 잡았지만,
  mpv 의 `frame-back-step` 을 쓰다가 나중에 갈아엎는 것보다 처음부터 계산해서 seek 하는 게
  코드가 더 적었다. 지금은 fps 기반이고, 2단계에서 PyAV PTS 인덱스로 바꾸면 VFR 까지 덮는다.
- **`frame-back-step` 이 실제로 틀리는 건 아직 못 봤다.** 계획서는 mpv issue #7208 을 근거로
  "뒤로 이동은 신뢰할 수 없다"고 썼는데, 위 계산 버그를 고친 뒤 다시 측정해 보니
  **이 세 파일에서는 mpv 도 정확했다** ([C] 항목). 우리 방식을 유지하는 이유는
  "mpv 가 틀렸다"가 아니라 2단계에서 PTS 인덱스로 갈아탈 길이 열려 있어서다.
  검증 스크립트의 [C] 항목은 앞으로도 계속 같이 돌면서 이 판단을 감시한다.
- **탭은 '재생' 하나만 만들었다.** 비교·트림 탭은 빈 껍데기로 만들어 두지 않았다.

**남은 것 · 걸린 것**

- **프레임 번호가 아직 추정값이다.** `time-pos × fps` 라서 CFR 에서만 정확하다.
  VFR 파일은 어긋난다. 전체 프레임 수도 mpv 의 `estimated-frame-count` 다.
  → 2단계에서 PyAV PTS 인덱스로 교체. UI 정보 패널에도 "추정"이라고 적어 뒀다.
- **프로젝트가 네트워크 드라이브(`Z:` = `\\192.168.1.100\Storage`)에 있다.**
  지금은 libmpv 로딩도 PySide6 import 도 문제없었지만(0.2초),
  5단계 PyInstaller 패키징 때 UNC 경로가 문제를 일으킬 수 있다.
- **`wait_until_playing()` 은 쓰면 안 된다.** `pause=True` 로 파일을 열기 때문에
  `core-idle` 이 영영 안 풀려서 그대로 멈춘다. `video-params` 속성이 올라오기를 기다리는
  방식으로 바꿨다 (`player.py`). 나중에 비교 모드에서 인스턴스를 2개 띄울 때도 같은 함정이 있다.
- **PowerShell `Start-Process` 로 띄우면 `MainWindowHandle` 이 0으로 나온다.**
  창은 정상적으로 뜨는데 프로세스 속성에 안 잡힌다. GUI 자동 검증은
  창 제목으로 찾거나(`EnumWindows`), `tools/smoke_gui.py` 처럼 앱 안에서 도는 게 낫다.
  `SendKeys.SendWait` 로 밖에서 키를 보내는 방식은 멈춰서 버렸다.
- **venv 의 `python.exe` 가 리다이렉터라 `Stop-Process` 로 안 죽는다.**
  실제 인터프리터가 따로 뜬다. 프로세스를 정리할 때는 둘 다 봐야 한다.
- 아직 없는 것: 캡쳐(3단계 아님, 2단계), 비교, 트림, 설정 저장, 디코더 선택 UI.
